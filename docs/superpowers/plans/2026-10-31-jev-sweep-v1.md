# jev-sweep v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local, open-source web app that sorts a Gmail inbox in batches with Jev. It auto-archives obvious junk, queues uncertain emails as generated review cards, and applies approved moves from an end-of-batch board.

**Architecture:**
- **Server:** one Node process (Hono) owns the whole pipeline: fetch from Gmail, ask Jev, run the policy, then queue or act. It persists everything to SQLite and streams state to the browser over SSE.
- **Browser:** a React app renders that state. The generative UI layer has two parts:
  - pure server functions, `decide` (Jev answers to a policy outcome) and `toCard` (outcome to a typed `CardSpec`);
  - a client card registry that renders a `CardSpec`.
- **External services:** Gmail, Jev and Claude each sit behind an interface with a fake implementation. The fake inbox mode runs with no accounts.

**Tech Stack:**
- Node ≥ 22 and TypeScript (strict, ESM)
- Server: Hono with `@hono/node-server`, `better-sqlite3`
- Service SDKs: `@typesafe-ai/sdk`, `@anthropic-ai/sdk`, `googleapis`
- Front end: React 18.3.1 and Vite
- Tests: Vitest, with `@testing-library/react` and jsdom for UI tests
- Dev tooling: `tsx`, `concurrently`

**Spec:** [`docs/superpowers/specs/2026-10-31-jev-sweep-design.md`](../specs/2026-10-31-jev-sweep-design.md). Reference UI: [`docs/prototype/session-flow.html`](../../prototype/session-flow.html).

## Global Constraints

- Node ≥ 22.12 (`"engines": {"node": ">=22.12"}`). This is required by `@typesafe-ai/sdk`.
- Keys live only on the server. The browser never receives `TYPESAFE_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_CLIENT_SECRET` or the Gmail token.
- Nothing person-specific goes in the repo: no hard-coded emails, labels, queries or paths. Secrets, tokens and the DB live in git-ignored `.env` and `data/`.
- Gmail actions are limited to: archive (remove `INBOX`), unarchive (add `INBOX`), add a label (creating it if needed), star, and mark read. Never trash, delete or mark spam. OAuth scope is `https://www.googleapis.com/auth/gmail.modify`.
- Folder moves are never applied until the user approves them on the board. Only `auto_archive` writes to Gmail mid-batch.
- **Dry run** (`settings.dryRun`) suppresses every Gmail write, including auto-archive.
- Jev model is pinned in config: `JEV_MODEL` defaults to `jev-1.14.0`. Never use `jev-latest`. Claude model: `CLAUDE_MODEL` defaults to `claude-haiku-5-5`.
- Default query: `in:inbox is:unread -category:promotions -category:social`. Default batch size: 20 (options 10/20/30/50). Jev concurrency: 6. Claude card-text timeout: 4000 ms.
- Body truncation: 2000 chars sent to Jev, 600 chars shown on cards.
- Design tokens:
  - font: SF Pro stack
  - sizes: 12/13/14/15/24
  - colors: `#7F7F7F #5D5D5D #292929 #F5F5F5 #F2F2F2 #E6E6E6`
  - red `#C2362B` is used only for important mail
- No UI kit. All motion respects `prefers-reduced-motion`.
- The UI never blocks on Jev or Claude.
- Ports: server 8787, Vite 5173. Vite proxies `/api` to the server.
- Branches and PRs: one PR per bucket, each on its own branch cut from `main` after the previous bucket's PR is merged. A fresh subagent reviews each PR and gives a go/no-go recommendation; the owner makes the merge call. Buckets:
  1. `b1-foundation`: Task 1
  2. `b2-decision-core`: Tasks 2–5
  3. `b3-storage-mail`: Tasks 6–7
  4. `b4-batch-engine`: Tasks 8–9
  5. `b5-api-sse`: Task 10
  6. `b6-web-ui`: Tasks 11–13
  7. `b7-docs-dry-run`: Task 14
  8. `b8-tuning`: Tasks 15–17 (after the first real run)
- Commit with the machine's git identity; never override `user.email`.

## Review Focus

1. **A thread changes in Gmail while queued or awaiting apply** (archived elsewhere, or a new message arrives). Apply re-checks it and skips it with a note instead of moving stale mail. Test in Task 9.
2. **"Other folder…" with a name that already exists in different case, or a nested name like `Finance/Tax`.** Reuse the existing label (case-insensitive match) instead of creating a duplicate. Test in Task 7.
3. **HTML-only, empty or huge email bodies.** Strip HTML to text, collapse whitespace and truncate. An empty body still produces a card (subject only). Test in Task 7.
4. **Browser reload, or a second tab, mid-batch.** The SSE connection gets a full `snapshot` first, then live events. Nothing is lost or duplicated. Test in Task 10.
5. **Answering the same email twice** (double click, or two tabs). `resolve` is idempotent. The second call is a no-op and doesn't advance the queue twice. Test in Task 8.

## Shared types (defined in Task 1, used everywhere)

```ts
// shared/types.ts
export type Dest = 'archive' | 'keep' | `label:${string}`;
export const NOUL_IDS = ['important','needs_reply','bulk_marketing','newsletter','automated_sender',
  'needs_attention','routine_financial','financial_exception','money_movement','transactional','dev_bot'] as const;
export type NoulId = typeof NOUL_IDS[number];
export interface Email { threadId: string; latestMessageId: string; fromName: string; fromAddress: string;
  subject: string; date: string /*ISO*/; labels: string[]; body: string; unread: boolean }
export interface JevAnswers { destination: { choice: Dest; confidence: number; probabilities: Partial<Record<Dest, number>> };
  nouls: Record<NoulId, number>; failed?: boolean }
export type Outcome = { kind: 'auto_archive' } | { kind: 'proposed'; dest: Dest }
  | { kind: 'queue'; card: 'filing' | 'important'; suggestKeep: boolean };
export interface CardOption { dest: Dest; label: string; p: number }
export interface CardSpec { kind: 'filing' | 'important'; threadId: string; n: number; fromName: string; fromAddress: string;
  subject: string; body: string; why?: string; summary?: string[]; options: CardOption[]; suggestKeep: boolean; gmailUrl: string }
export type DecisionStatus = 'auto_applied' | 'proposed' | 'applied' | 'skipped' | 'failed';
export interface Decision { threadId: string; n: number; subject: string; fromName: string; dest: Dest; who: 'jev' | 'you';
  important: boolean; star: boolean; opened: boolean; status: DecisionStatus; note?: string }
export interface QueueItem { threadId: string; n: number; subject: string; important: boolean }
export type BatchStatus = 'running' | 'reviewing' | 'applying' | 'applied' | 'discarded';
export interface BatchView { sessionId: string; batchId: string; batchNo: number; total: number; read: number;
  status: BatchStatus; paused: boolean; dryRun: boolean; decisions: Decision[]; queue: QueueItem[]; current: CardSpec | null }
export interface Folder { name: string; enabled: boolean; description?: string }
export interface Thresholds { guardNoul: number; importantQueue: number; needsReplyQueue: number;
  autoArchiveConfidence: number; proposeConfidence: number; recentDays: number }
export interface Settings { query: string; batchSize: 10 | 20 | 30 | 50; folders: Folder[]; thresholds: Thresholds; dryRun: boolean }
export interface SessionSummary { id: string; startedAt: string; batches: number; total: number;
  split: { archived: number; filed: number; you: number; important: number }; unfinishedBatchId?: string }
export interface SetupStatus { typesafe: boolean; anthropic: boolean; google: boolean; gmailConnected: boolean;
  foldersChosen: boolean; fake: boolean }
export type SessionEvent =
  | { type: 'snapshot'; view: BatchView }
  | { type: 'decided'; decision: Decision }            // Jev auto/proposed, or a human answer, or a board move
  | { type: 'queued'; item: QueueItem }
  | { type: 'current'; card: CardSpec | null }
  | { type: 'card_text'; threadId: string; why?: string; summary?: string[] }
  | { type: 'progress'; read: number; total: number; paused: boolean }
  | { type: 'status'; status: BatchStatus }
  | { type: 'apply_step'; label: string; count: number; done: boolean }
  | { type: 'error'; message: string };
```

### Task 3: Policy, `decide()` (gen UI step 1)

**Files:**
- Create: `server/policy/decide.ts`
- Test: `tests/server/policy/decide.test.ts`

**Interfaces:**
- Consumes: `JevAnswers`, `Outcome`, `Thresholds`.
- Produces:
  - `triageSaysArchive(n: Record<NoulId, number>, ageDays: number, recentDays: number): boolean`
  - `decide(a: JevAnswers, ageDays: number, t: Thresholds): Outcome`

**Port `triageSaysArchive` from `inbox-triage/score.py` `decide()`.** It returns true exactly where that function returns `"archive"`, with the same constants (0.95/0.25 for recent mail; 0.85/0.5, 0.93/0.65, 0.9/0.5/0.5, 0.85, 0.85/0.3 and 0.85/0.8 for older mail; newsletter +0.05).

**`decide` evaluates in this order** (spec §6.4):
1. `a.failed` → `{queue, filing, suggestKeep:false}`
2. `important ≥ importantQueue` → `{queue, important, suggestKeep: needs_reply ≥ needsReplyQueue}`
3. `needs_reply ≥ needsReplyQueue` → `{queue, filing, suggestKeep:true}`
4. `guard` is `financial_exception ≥ guardNoul || money_movement ≥ guardNoul || automated_sender < guardNoul || important ≥ guardNoul`. If `!guard && triageSaysArchive(...) && destination.choice==='archive' && destination.confidence ≥ autoArchiveConfidence` → `{auto_archive}`
5. If `!guard && destination.choice !== 'archive' && destination.confidence ≥ proposeConfidence` → `{proposed, dest}`
6. Otherwise → `{queue, filing, suggestKeep:false}`

**Interfaces:**
- Consumes: `Email`, `JevAnswers`, `Outcome`, `CardSpec`, `Folder`.
- Produces:
  - `interface CardText { why?: string; summary?: string[] }`
  - `interface CardTextWriter { write(email: Email, a: JevAnswers, kind: 'filing'|'important'): Promise<CardText> }`
  - `class ClaudeWriter implements CardTextWriter` (constructor `(apiKey: string, model: string, client?: Anthropic)`)
  - `class FakeWriter implements CardTextWriter` (canned `why`; `summary` from a fixture field)
  - `withTimeout(w: CardTextWriter, ms: number): CardTextWriter` (resolves `{}` on timeout or error)
  - `toCard(email: Email, n: number, a: JevAnswers, outcome: Extract<Outcome,{kind:'queue'}>, text: CardText): CardSpec`

**Rules for `toCard`:**
- `options` are the top 3 entries of `a.destination.probabilities`, sorted by `p` descending. Labels are:
  - `archive` → `Archive`
  - `keep` → `Keep in inbox`
  - `label:X` → `X`
- `body` is `truncate(email.body, 600)` (from Task 7's `provider.ts`; until then, a local helper that Task 7 replaces).
- `gmailUrl` is `https://mail.google.com/mail/u/0/#all/<threadId>`.
- If `a.failed`, `options` is `[]`.

**`ClaudeWriter`:**
- One `messages.create` call with `max_tokens` 300 and the system prompt:
  > You write short helper text for an email triage card. Reply with JSON only: {"why": one sentence under 15 words saying why a human should decide this email} and, only if asked for a summary, {"summary": 2-4 bullets under 12 words each covering dates, amounts, requests and attachments}. Never invent facts that are not in the email.
- The user content holds the email fields (subject, from, body truncated to 2000) and Jev's top two destinations with probabilities and confidence, so `why` can name the split.
- Parse the JSON. On a parse failure, return `{}`.

### Task 8: BatchRunner

**Files:**
- Create: `server/session/runner.ts`
- Test: `tests/server/session/runner.test.ts`

**Interfaces:**
- Consumes: `MailProvider`, `JevClient`, `CardTextWriter`, `Repo`, `ReviewQueue`, `decide`, `toCard`, `ageDays`, `Settings`, `SessionEvent`.
- Produces `class BatchRunner`:
  - `constructor(deps: { mail: MailProvider; jev: JevClient; writer: CardTextWriter; repo: Repo; emit: (batchId: string, e: SessionEvent) => void; concurrency: number; now?: () => Date })`
  - `start(sessionId: string): Promise<string /*batchId*/>`: reads settings (query, batchSize, folders, thresholds, dryRun) from `repo.getSettings()`
  - `resume(batchId: string): Promise<void>`
  - `pause(batchId: string): void`
  - `continue(batchId: string): void`
  - `resolve(batchId: string, threadId: string, dest: Dest, opts?: { star?: boolean }): void`
  - `jumpTo(batchId: string, threadId: string): void`
  - `move(batchId: string, threadId: string, dest: Dest): void` (board drag; sets `who:'you'`)
  - `view(batchId: string): BatchView`
  - Returns events through `emit`.

**Behavior:**
1. **Fetch.** `start` creates the batch, fetches `batchSize` emails (`repo.excludedThreads()`), saves them, sets status `running`, and emits `snapshot`.
2. **Ask Jev.** Process emails through a pool of `concurrency`. For each email: `jev.ask` (on throw, use `{failed:true}` answers with an empty destination) → `repo.saveJev` → `decide`.
3. **Act on the outcome:**
   - `auto_archive`: call `mail.archive` unless `dryRun`; save the decision with `status:'auto_applied'` and `who:'jev'` (note `dry run` in dry-run mode); emit `decided`.
   - `proposed`: save the decision as `proposed`, `who:'jev'`; emit `decided`.
   - `queue`: push a `QueueItem` (`important` = `card==='important'`), emit `queued`, and start `withTimeout(writer)` without awaiting it. When it settles: `saveCardText`, emit `card_text`, and if this email is `current`, re-emit `current` with the updated card. If nothing is current, advance (see 4).
4. **Advance.** If there's no current card, `queue.shift()`, build the card with `toCard` (using whatever text is stored so far), set it as current, and emit `current`. Persist the queue after every change (`repo.saveQueue`).
5. **Resolve.** `resolve`: if `threadId` is not current and not in the queue, it's a **no-op** (idempotent). Otherwise:
   - save the decision as `who:'you'`, `status:'proposed'`, `star: opts.star ?? false`, `opened: card.kind==='important'`, `important: card.kind==='important'`;
   - emit `decided`;
   - clear current and advance.
6. **Jump.** `jumpTo`: `queue.unshift(currentItem)`, then `queue.take(threadId)`, which becomes current.
7. **Progress.** Emit `progress` after each Jev answer.
8. **Batch done.** When every email has a Jev answer, the queue is empty and there's no current card: set status `reviewing` and emit `status`.
9. **Pause.** `pause` stops new Jev calls (in-flight ones finish); `continue` restarts the pool.
10. **Resume.** `resume(batchId)` rebuilds state from `repo.loadBatch`, re-fetches with `mail.getThread` only the emails still in the queue or current (a `null` result becomes a `skipped` decision with note `changed in Gmail`), and continues processing emails with no stored Jev answer.

**Interfaces:**

  - Gmail: page through `threads.list` for IDs. Then walk oldest first, calling `threads.get` with `format: 'minimal'` (message IDs only) with up to 8 calls in flight. Skip a thread when its ID and latest message ID match `excluded`. Stop at `n` candidates.
- `getThread` (already exists) fetches each candidate in full. The runner fetches with up to 8 in flight and pushes each email into the Jev pool the moment it arrives.
- `BatchRunner.start` creates the batch and emits `snapshot` with `total` set to the candidate count. It returns the batch ID right after listing, before any full fetch.
  - Each fetched email is saved and emitted (the existing `progress` event gains `fetched`).
  - A `getThread` that returns null is recorded as `skipped` / `changed in Gmail`.
  - Fetch errors follow the existing failed-decision rule.
- Resume: a batch that crashed mid-fetch keeps its saved emails. Any missing candidates are fetched again through `getThread`. `total` stays correct.
- Session screen: while `fetched < total`, the header says "Fetching from Gmail… {fetched} of {total}". The ticker fills as emails arrive.

- An excluded thread with the same latest message ID is never fetched in full.

### Task 16: Policy v2 and the stale question

**Files:**
- Modify: `shared/types.ts` (add `stale` to `NOUL_IDS`; `Thresholds` gains `staleDays: 14`, `staleConfidence: 0.85`, `junkMaxKeep: 0.15`), `server/config.ts` (defaults), `server/jev/questions.ts`, `server/policy/decide.ts`, `fixtures/fake-inbox.json`
- Test: decide, questions, fixture

**Jev state and questions:**
- State gains `today` (an ISO date).
- `important` becomes: "Does this email contain something this person needs to know or do **today** (a deadline, appointment, bill, security problem, or request) given how old it is?"
- New noul `stale`: "Given today's date and how old this email is, has the event, deadline, offer, alert, code, delivery or announcement it is about already passed, so that it no longer matters? Examples: past maintenance or outages, expired codes and sign-in alerts that were never acted on, ended sales and webinars, past appointments, deliveries that already arrived, old onboarding or welcome mail. Mail that stays useful as a record (receipts, contracts, tax documents, statements) is not stale."
- The 9 inbox-triage nouls stay verbatim, and `triageSaysArchive` stays a straight port, so the score.py parity test holds.

**`decide` order:**
1. `failed` → queue filing.
2. **Stale rule.** All of these must hold:
   - `ageDays >= staleDays`
   - `stale >= staleConfidence`
   - `automated_sender >= 0.9`
   - `needs_reply < 0.3`
   - `financial_exception < 0.5`
   - `money_movement < 0.5`

   Then `auto_archive`. This is checked **before** the `important` rule.
3. `important >= importantQueue` → queue important (unchanged).
4. `needs_reply >= needsReplyQueue` → queue filing with keep suggested (unchanged).
5. `guard` is as before.
6. **Junk rule.** If `!guard`, `triageSaysArchive(...)`, and `probabilities.keep ?? 0` is at most `junkMaxKeep`:
   - if `choice` is a label and `confidence >= proposeConfidence` → `proposed(choice)`;
   - otherwise → `auto_archive`.
7. **Existing archive rule** (unchanged): `!guard`, triage says archive, `choice === 'archive'`, and `confidence >= autoArchiveConfidence` → `auto_archive`.
8. **Existing propose rule** (unchanged).
9. Otherwise → queue filing.
